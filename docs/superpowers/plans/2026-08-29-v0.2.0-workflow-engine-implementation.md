# v0.2.0 Workflow Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the approved plugin-native workflow engine with strict definitions, deterministic permissions and commands, immutable DAG scheduling, persistent background runs, configurable workspaces, and adversarial verification.

**Architecture:** Keep the engine as pure TypeScript modules under `src/workflow/`, with adapters for OpenCode sessions, Git/filesystem workspaces, clocks, processes, and XDG state. Validate and compile everything before scheduling; runtime state and evidence are authoritative, while native OpenCode sessions perform model work asynchronously.

**Tech Stack:** TypeScript, Bun, `@opencode-ai/plugin`/`@opencode-ai/sdk` 1.18.x, Zod 4.1.8 for strict parsing, Git CLI through fixed argv, native OpenCode `session.create`/`session.promptAsync`/`session.abort`, uv-managed pre-commit.

**Spec:** `docs/superpowers/specs/2026-08-29-v0.1.1-v0.2-workflow-engine-design.md`

## Global Constraints

- Preserve the existing `/swarm` agents and command unchanged unless a focused compatibility change is tested.
- Unknown schema fields, enum values, capabilities, paths, commands, state transitions, and workspace identities fail closed.
- Effective policy is `installation ∩ launch approval ∩ workflow ceiling ∩ step request`; explicit deny wins.
- Workflow and policy hashes, approved DAGs, and run evidence are immutable or append-only as specified.
- Commands use direct executable/argv arrays; shell composition, privileged operations, pushes, merges, releases, publication, and external writes have no workflow capability.
- Worktree isolation is supported but not mandatory; current-workspace writes require explicit declaration, installation permission, launch approval, and granular capabilities.
- Run state is XDG repository-keyed, sanitized, atomically written, and never auto-resumed.
- Implementation subagents run on `gpt-5.6-luna` at medium reasoning effort; runtime workflow models remain user-configured and model-agnostic by default.
- Every task ends with focused tests and a commit; the final release requires `bun run check`, `bun run package:check`, and `uvx --from pre-commit==4.6.2 pre-commit run --all-files`.

### Task 7: Schedule native OpenCode sessions

**Files:**
- Create: `src/workflow/runtime.ts`
- Test: `src/workflow/runtime.test.ts`

**Interfaces:**
- Consumes: `WorkflowPlan`, `RepositoryStateStore`, workspace manager, policy/command compilers.
- Produces `WorkflowRuntime.launch`, `.status`, `.wait`, `.cancel`, `.amend`,
  `.resume`, and `.cleanup`; native session adapter calls
  `client.session.create`, `client.session.promptAsync`, `client.session.status`,
  and `client.session.abort`.

The runtime interface is:

```ts
interface WorkflowRuntime {
  launch(plan: WorkflowPlan, approval: LaunchApproval): Promise<{ runId: string }>
  status(runId: string): Promise<RunRecord>
  wait(runId: string, timeoutMs: number): Promise<RunRecord>
  cancel(runId: string): Promise<RunRecord>
  amend(runId: string, input: unknown): Promise<{ revision: number; approval: ApprovalSummary }>
  resume(runId: string, approval: LaunchApproval): Promise<RunRecord>
  cleanup(runId: string): Promise<CleanupResult>
}
```

- [ ] **Step 1: Write failing scheduler tests**

Use fake sessions and a fake clock to prove launch returns a run ID before
completion, independent steps run up to `maxConcurrency`, dependents wait for
successful outputs, fail-fast and continue-independent differ, cancellation
stops new scheduling and signals active sessions, lost sessions become failed,
and model output cannot forge runtime status.

- [ ] **Step 2: Run tests to verify failure**

Run: `bun test src/workflow/runtime.test.ts`

Expected: FAIL because runtime is absent.

- [ ] **Step 3: Implement launch and scheduling**

Atomically persist `awaiting-approval`/`running` state before scheduling. Create
one native child session per step, send a prompt containing only validated
inputs, output contract, tools, and effective policy, and use `promptAsync`.
Poll through event/status adapters with bounded waits rather than busy loops.
Persist every transition and validated structured output. Schedule ready steps
in stable order and enforce failure policy.

- [ ] **Step 4: Implement cancellation, amendments, resume, cleanup**

Cancellation aborts active session IDs and preserves workspaces. Amendments
create a new revision and require a fresh approval summary before scheduling.
Resume revalidates repository revision, workflow/policy hashes, workspace, and
installation policy; mismatches transition to `stale`. Cleanup delegates to
lossless workspace checks and retains evidence.
