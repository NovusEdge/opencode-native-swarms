# v0.1.1 Hardening and v0.2.0 Workflow Engine Design

Status: Draft — design approved in conversation; written review pending

## Goal

Deliver two deliberately separate releases:

1. `v0.1.1` closes the tester-command gap discovered while dogfooding
   `v0.1.0`, without broadening the stage-one security model.
2. `v0.2.0` adds a plugin-native workflow engine that lets users and models
   define, approve, launch, observe, amend, resume, and clean up bounded
   background-agent workflows while the primary OpenCode conversation remains
   available.

The workflow engine must make authority deterministic. A model may propose a
workflow and request permissions, but it cannot grant itself authority. The
effective policy is compiled from user-controlled ceilings, every elevated
operation remains visible at approval time, and unknown or ambiguous behavior
fails closed.

## Non-goals

Neither release will:

- replace OpenCode's native session or subagent implementation;
- introduce a required daemon or separate MCP service;
- pin a model globally or require a particular model provider;
- expose direct workflow capabilities to push, merge, publish packages, create
  releases, or write to external services;
- execute arbitrary shell programs through a permissive wildcard;
- make worktrees mandatory for every workflow;
- silently resume work after a plugin or OpenCode restart;
- allow a running workflow to mutate its approved DAG or permission ceiling;
- publish the package to npm as part of these releases.

The existing `/swarm` workflow remains supported. The new engine is additive
in `v0.2.0`; migration to a declarative workflow is optional.

## Release boundaries

### v0.1.1: tester hardening

The patch release adds two exact, argument-free commands to the
`swarm-tester` allowlist:

- `bun run check`
- `bun run typecheck`

It preserves the existing default deny. Variants with added arguments, shell
composition, environment assignments, or other script names remain denied.
Regression tests must prove both the new allows and representative denials.
Documentation and dogfood evidence must reflect the supported commands.

The release closes GitHub issue #3 only after the real installed plugin can run
the repository's canonical check through `swarm-tester`. The patch receives a
reviewed pull request, passes the existing quality gates, and is published as
an annotated `v0.1.1` GitHub release.

### v0.2.0: declarative workflow engine

The minor release adds strict workflow definitions, deterministic policy
compilation, immutable approved DAGs, background scheduling, persistent run
state, configurable workspace isolation, and structured inspection tools. It
receives its own reviewed pull request, dogfood report, release notes, and
annotated `v0.2.0` GitHub release after `v0.1.1` is complete.

## Architecture

The engine lives inside the existing TypeScript OpenCode plugin. It uses native
OpenCode background sessions rather than emulating agents in a separate
process. Its internal modules have narrow responsibilities:

- **workflow-schema** parses strict, versioned JSON and produces a normalized
  workflow definition.
- **policy-compiler** intersects all applicable policy layers, compiles command
  rules, and emits a canonical effective-policy hash.
- **workflow-planner** validates the DAG, scopes, dependencies, workspace
  choices, and concurrency before freezing an approved revision.
- **agent-compiler** converts validated step prompts, model requests, tool
  access, and effective permissions into native OpenCode agent definitions.
- **workflow-runtime** schedules ready steps and tracks their native background
  sessions without blocking the primary conversation.
- **workspace-manager** resolves and validates `read-only`, `current`,
  `worktree`, and `existing` workspace modes.
- **state-store** writes atomic, repository-keyed run state and sanitized
  evidence beneath the XDG state directory.
- **tool surface** exposes validation, lifecycle, inspection, and cleanup to
  OpenCode commands and models.

Module boundaries are internal implementation details, not separate services.
They should remain independently testable so that a future daemon extraction
is possible if actual usage demonstrates a need for process independence.

## Workflow definitions

### Sources and revisions

Persistent definitions live at `.opencode/workflows/*.json`. An inline
definition uses the identical schema and is ephemeral unless the user approves
saving it. A model may author either form, but saving a model-authored file is
a repository write and therefore requires the corresponding approval.

Every normalized definition has:

- `schemaVersion`, initially `1`;
- a stable workflow `name`;
- an optional human-readable `description`;
- a workflow-level failure policy and concurrency limit;
- a workflow permission ceiling;
- permitted workspace modes and defaults;
- one or more uniquely named steps;
- a canonical workflow hash calculated after normalization.

Unknown fields are rejected at every object level. Unknown enum members are
rejected. Version changes require an explicit migration or a new schema parser;
the engine never guesses how to interpret a newer definition.

### DAG validation

Before approval, the planner rejects:

- missing or duplicate step IDs;
- references to missing dependencies or outputs;
- cycles, including self-dependencies;
- inputs that are not backed by a transitive dependency;
- incompatible output types;
- concurrency outside installation limits;
- invalid workspace modes or repository identities;
- read or write scopes outside the workflow ceiling;
- overlapping parallel writer scopes;
- commands or capabilities unavailable under the compiled policy.

The approved DAG is immutable for the lifetime of a run. A running agent can
produce an amendment proposal, but it cannot add or alter a step directly.

## Permission model

### Deterministic intersection

Effective authority is the intersection of four ordered ceilings:

```text
installation policy
    ∩ launch approval
    ∩ workflow ceiling
    ∩ step request
    = effective step policy
```

An explicit deny at any layer wins. A model-provided deny can narrow authority
but never cancel a deny or add authority. Missing capabilities, unknown
capabilities, unknown paths, and malformed rules are denied.

The compiler normalizes the complete effective policy to canonical JSON and
records its cryptographic hash with the approved workflow revision and run.
Each decision can identify the layer and rule that allowed or denied it.

### Capability enums

The initial granular capability vocabulary is:

- repository: `repo.read`, `repo.search`;
- Git inspection: `git.status`, `git.diff`, `git.log`;
- Git mutation: `git.stage`, `git.commit`;
- web: `web.search`, `web.fetch`;
- verification: `test.run`, `typecheck.run`, `lint.run`, `build.run`;
- workspace: `workspace.patch`, `workspace.create`, `workspace.delete`;
- coordination: `agents.spawn`, `agents.message`, `agents.wait`.

`workspace.patch`, `workspace.create`, `workspace.delete`, `git.stage`, and
`git.commit` require explicit launch approval whenever present in an effective
policy. They are never implied by a writable workspace mode. File patching,
creation, deletion, staging, and committing are separate operations even when
one step requests several of them.

There is intentionally no capability for push, merge, release creation,
package publication, privileged execution, remote shell access, or arbitrary
external-service writes in `v0.2.0`.

### Models and generated agents

Workflow steps are model-agnostic by default and use the user's configured
OpenCode model. A definition may request inheritance from the launching model
or a configured model alias when installation policy permits it. Raw provider
credentials never appear in workflow definitions or run evidence.

The agent compiler builds a native agent for each step from its validated
prompt, effective capability set, structured input contract, structured output
contract, and runtime limits. Generated agents cannot address undeclared tools
or communicate outside declared coordination capabilities.

## Command policy

### Structured rules

Command execution uses data, not shell strings. A rule specifies:

- an executable name or resolved approved executable;
- exact or position-constrained argument vectors;
- a repository-contained working directory;
- an explicit environment-variable allowlist with values supplied by the
  runtime rather than the model;
- a timeout and output limit bounded by installation policy.

Every command set has `default: "deny"`, plus allow and deny lists. The
installation deny floor is immutable at runtime. Workflow and step denies may
only narrow the result. A step may select a named operation exposed by the
plugin, which is preferred, or request an exact argument vector that is shown
at launch approval.

### Parsing and denial

If user input or a migrated definition supplies command-like text, the engine
parses it into a shell AST only to determine whether it is one unambiguous
simple command that can be represented structurally. The engine rejects shell
composition in `v0.2.0`, including:

- pipes and redirects;
- command or process substitution;
- `&&`, `||`, and command lists;
- backgrounding;
- functions, aliases, and shell built-ins that evaluate code;
- inline environment assignments not represented by approved environment
  fields;
- unresolved globs or expansions.

The immutable installation deny floor also blocks privileged executables,
remote shells, package publication, Git force-push and push operations, release
operations, and known external-write clients. An executable absent from the
allowlist is denied even when it is not explicitly named by the deny floor.

The runtime launches the approved executable directly with an argument array,
a sanitized environment, the approved contained working directory, optional
stdin disabled unless explicitly modeled, a deterministic timeout, and a
bounded captured output. Approval records the canonical compiled command and
policy decision, not merely the source text.

### Trusted-project boundary

Command policy controls which process invocation the engine makes; it does not
prove what repository-owned code does after that process starts. For example,
an exact `bun run check` may execute scripts chosen by the repository. Without
an installation-configured operating-system sandbox, those scripts can write
files, access the network, or start child processes independently of the
plugin's tool permissions.

Therefore `v0.2.0` preserves the stage-one trusted-project rule for every
repository-owned command. The approval view labels such commands as trusted
project code. `read-only` means the generated agent and plugin tools receive no
repository-write authority; it is not advertised as an OS sandbox for an
approved subprocess. Installation policy may require a supported sandbox
runner or deny commands entirely. An OS-sandbox backend is not required for
the initial release, and the engine must never claim that command allowlists
alone provide process containment.

## Runtime and persistence

### Launch and scheduling

`workflow_launch` validates and compiles a definition, presents its approval
summary when required, atomically creates a run record, and returns a run ID
without waiting for completion. This keeps the primary conversation available.

The scheduler starts only steps whose dependencies succeeded and whose
resources fit the approved concurrency limit. Independent steps may run in
parallel. Each step receives its own native OpenCode background session,
compiled agent, effective policy, workspace binding, declared inputs, and
output contract.

Steps exchange only declared structured outputs and artifact references.
They do not inherit other agents' unrestricted transcripts. The runtime
validates a returned output against its declared type before making it
available downstream; model text cannot forge runtime status or evidence.

### Failure policies

A workflow chooses one of:

- `fail-fast`: after the first terminal failure, schedule no new steps and
  cancel active steps where safe;
- `continue-independent`: allow unaffected branches to finish, skip descendants
  of failed dependencies, and report the partial result.

Cancellation stops new scheduling, signals active sessions, and preserves run
state, evidence, and workspaces. A native session that cannot be found or
reattached becomes a visible failed step with a stable failure reason; it is
never silently relaunched.

### State machines

Workflow state transitions are:

```text
draft -> awaiting-approval -> running -> succeeded
                                      -> failed
                                      -> cancelled
                                      -> stale
```

Step state transitions are:

```text
queued -> ready -> running -> succeeded
                           -> failed
                           -> cancelled
queued -------------------> skipped
ready --------------------> cancelled
```

Invalid transitions are rejected. State is written atomically before a session
is scheduled and after every accepted transition.

### XDG storage and repository identity

Run state is stored outside the repository under the platform's XDG state
directory, namespaced by this plugin and keyed by a stable repository identity.
The identity combines the canonical Git common directory with repository
metadata; a bare path string alone is insufficient. State includes:

- run ID, workflow source, revision, and canonical hash;
- repository and workspace identities;
- approval record and effective-policy hash;
- step states, native session references, and timestamps;
- sanitized command outcomes and declared outputs;
- artifact references, modified paths, and created commits;
- cancellation, failure, amendment, resume, and cleanup events.

Secrets, raw credentials, unrestricted transcripts, and unsanitized process
environments are never written to run evidence.

### Restart and resume

The plugin does not auto-resume after OpenCode or the plugin restarts. Explicit
`workflow_resume` revalidates:

- repository identity and revision;
- workflow revision and canonical hash;
- effective-policy hash and current installation policy;
- workspace existence, ownership, and expected Git state;
- completed outputs and remaining step dependencies.

Any mismatch marks the run `stale`. Continuing then requires either an approved
amendment that records the changed facts or a new run. Resume never treats
changed policy as implicitly approved.

### Amendments

`workflow_amend` creates a new immutable workflow revision linked to the prior
one. It presents the full new approval summary and highlights all changes,
especially new permissions, widened paths, new commands, workspace changes,
and additional steps. An amendment cannot hide new authority in a diff-only
view. No revised step is scheduled before approval.

## Workspace modes

Worktree isolation is supported and recommended for writing workflows, but it
is configurable rather than mandatory.

### read-only

`read-only` exposes a validated repository view with no plugin-granted write
capabilities. It is the default for research, testing, and review steps. A
command may still be denied when it is known to write caches or snapshots
unless policy provides an isolated writable scratch location that is not the
repository. Approved subprocesses retain the trusted-project limitation
described in the command policy.

### current

`current` binds the current checkout. Read-only use requires no special write
approval. Writes require all of the following:

- the workflow explicitly selects current-worktree writes;
- installation policy permits them;
- launch approval lists the mode and exact write scopes;
- the step has the necessary granular workspace capabilities;
- any configured clean-worktree precondition passes.

Existing dirty changes are snapshotted in evidence and preserved. The engine
never reverts an unrelated change.

### worktree

`worktree` creates or adopts a plugin-managed Git worktree on an approved,
non-protected branch. It is the default recommendation for steps that patch,
create, delete, stage, or commit files. Creation details and the cleanup policy
are visible at approval.

### existing

`existing` binds a pre-existing registered Git worktree. The engine validates
its repository identity, canonical path, branch, ownership record, and expected
revision before use. Merely naming an arbitrary directory does not register it.

### Writer safety

All modes enforce canonical path containment and recheck resolved symlinks.
Installation policy defines protected files and directories that cannot be
written even when a broader glob appears approved.

Each writer step owns explicit path scopes. Parallel writer steps with
overlapping scopes are rejected. Sequential sharing is allowed only through an
explicit dependency and workspace handoff. The handoff records the expected
tree or commit state; hidden shared mutable state is not assumed.

Staging validates every staged path against the effective write scopes.
Committing requires `git.commit`, explicit approval, a non-protected branch,
and a staged-path revalidation immediately before commit. A failed or cancelled
run retains its workspace by default.

Cleanup is always explicit in `v0.2.0`. It refuses to remove a workspace that
contains unrecorded changes, unpushed commits, an identity mismatch, or any
other condition that could lose work. Run evidence survives workspace cleanup.

## User and model interface

### Tools

The plugin exposes:

- `workflow_validate`: parse, normalize, and report schema or policy errors;
- `workflow_launch`: compile, approve as needed, start, and return a run ID;
- `workflow_save`: persist an approved inline definition;
- `workflow_inspect`: show normalized definitions, revisions, and compiled
  policies without launching;
- `workflow_status`: return current workflow and step state;
- `workflow_wait`: await a bounded state change without busy polling;
- `workflow_cancel`: request cancellation and preserve evidence;
- `workflow_amend`: propose and approve a new immutable revision;
- `workflow_resume`: revalidate and explicitly resume an interrupted run;
- `workflow_cleanup`: safely remove eligible managed workspaces.

Every lifecycle tool is scoped to the active repository identity unless the
user explicitly selects another registered repository through a supported
interface.

### Commands

Human-facing commands provide concise wrappers:

```text
/workflow validate <name-or-path>
/workflow run <name-or-path>
/workflow status <run-id>
/workflow cancel <run-id>
/workflow resume <run-id>
/workflow cleanup <run-id>
```

Inline model-authored workflows use the tools directly and remain inspectable
by these commands after launch.

### Approval view

Before a workflow with approval-bound behavior launches, the user sees:

- definition source, schema version, revision, and workflow hash;
- repository, workspace paths, modes, branches, and expected revisions;
- steps, descriptions, models, dependencies, and maximum concurrency;
- effective capability ceiling and the policy layers that produced it;
- exact read and write scopes;
- compiled executable and argument arrays;
- patch, create, delete, stage, and commit authority;
- timeouts, output limits, and child-agent limits;
- effective-policy hash and any differences from a prior revision.

Approval is bound to the displayed workflow and policy hashes. Changes after
approval invalidate it.

Model-authored workflows, repository writes, command execution, deletion,
staging, and commits always require an interactive launch approval in
`v0.2.0`. Installation policy may pre-approve an exact persistent read-only
workflow revision that has no commands or elevated capabilities. In that case,
the recorded launch-approval layer is the stored grant bound to the same
workflow and policy hashes; it is not omitted from policy intersection.

### Notifications

Notifier integration is optional. When configured, it may report a terminal
success, partial result, failure, cancellation, or stale run with its run ID.
Notifications are not authoritative and contain no sensitive output. The
plugin's persisted state and query tools remain the source of truth.

## Errors, evidence, and observability

Validation errors contain a stable machine-readable code and the exact JSON
path. Permission denials identify the policy layer and rule. Runtime errors
identify the run, step, operation, and state transition without exposing
secrets.

Evidence is deterministic and bounded. For each executed command it records
the compiled executable and arguments, contained working directory, start and
finish time, exit status or signal, truncation status, and sanitized bounded
output. For workspace activity it records allowed and affected paths, tree or
commit identifiers, and validation outcomes. For agents it records native
session identifiers and declared outputs, not unrestricted transcripts.

`workflow_status` distinguishes facts from model-produced content. A model
cannot mark its own step successful; the runtime does so only after the native
session completes and all required outputs validate.

## Security invariants

The implementation must preserve these invariants:

1. Models request authority; only user-controlled policy and approval grant it.
2. Effective authority can only narrow as policy layers are intersected.
3. Unknown schema, capability, command, path, state, or workspace values fail
   closed.
4. Approved DAGs, workflow hashes, and policy hashes are immutable within a
   run.
5. Commands execute as direct argument arrays, never through implicit shell
   evaluation.
6. Repository writes require both a writable mode and granular write
   capabilities; neither implies the other.
7. Parallel writers never own overlapping paths.
8. Restart, drift, or identity mismatch never causes silent continuation.
9. Cancellation and cleanup never discard unrecorded user or agent work.
10. Direct workflow capabilities for pushes, merges, releases, publication,
    privileged execution, remote shells, and external-service writes do not
    exist. Repository-owned commands remain subject to the documented
    trusted-project boundary unless an OS sandbox enforces more.

## Testing strategy

### v0.1.1

Focused tests cover:

- exact allow for `bun run check` and `bun run typecheck`;
- denial of added arguments and different script names;
- preservation of the wildcard deny and existing allowed commands;
- resolved OpenCode configuration containing the new exact rules.

The real installed plugin is dogfooded against this repository before release.

### v0.2.0 automated tests

The suite includes:

- schema tests for normalization, unknown fields, enums, versions, references,
  cycles, and stable error paths/codes;
- policy tests for intersection, deny precedence, unknown capability denial,
  path containment, canonicalization, and stable hashes;
- command tests for exact argv matching, deny-floor precedence, sanitized
  environments, limits, and rejection of every unsupported shell construct;
- scheduler tests for readiness, concurrency, both failure policies,
  cancellation, immutable DAGs, and lost sessions;
- state tests for atomic transitions, repository namespacing, restart, resume,
  drift, stale runs, and evidence redaction;
- workspace tests for all four modes, dirty state preservation, registration,
  protected paths, symlink escapes, writer overlap, handoffs, stage validation,
  commits, and lossless cleanup;
- adversarial tests for permission escalation, forged status/output, hidden
  shell composition, overlapping globs, policy-hash changes, and amendment
  laundering.

Tests should favor pure policy and state-machine units, with integration tests
at OpenCode and Git boundaries. Time, process, filesystem, and session adapters
must be injectable where needed for deterministic tests.

### v0.2.0 dogfood matrix

The release candidate runs and documents:

- a persistent read-only workflow;
- an ephemeral model-authored workflow that is not saved;
- a current-workspace write with explicit approval;
- an isolated worktree write and explicit cleanup;
- cancellation while independent steps are active;
- restart followed by explicit successful resume;
- drift followed by a `stale` result;
- a rejected permission-escalation proposal;
- a rejected command-composition attempt;
- an approved amendment that creates a new visible revision.

Dogfood reports contain sanitized evidence, not private transcripts or secrets.

## Release gates

### v0.1.1 gate

`v0.1.1` may be released when:

- issue #3 is reproduced by a regression test and fixed;
- the installed-plugin dogfood check succeeds;
- focused tests, `bun run check`, package validation, and pre-commit pass;
- documentation and release notes match the behavior;
- a reviewed pull request is merged with the required CI check green;
- the annotated tag targets the tested merge commit.

### v0.2.0 gate

`v0.2.0` may be released when:

- every security invariant has direct automated coverage;
- the full workflow dogfood matrix is documented;
- no release-blocking correctness, containment, permission, persistence, or
  cleanup defect remains open;
- focused and repository-wide quality checks pass on the candidate;
- the package contents exclude run state, dogfood secrets, and local artifacts;
- a separate reviewed pull request is merged with required CI green;
- release notes explain the experimental native-subagent requirement, workspace
  risks, approval semantics, and unsupported operations;
- the annotated tag targets the tested merge commit.

## Implementation process constraint

After this written specification is approved, implementation receives a
separate task-level plan with review checkpoints. Implementation subagents used
for that work run on `gpt-5.6-luna` at medium reasoning effort, as requested;
this constraint does not pin or otherwise affect models selected by plugin
users at runtime.

## Completion criteria

The work is complete when `v0.1.1` has closed the tester-command defect and
`v0.2.0` provides the approved workflow engine with deterministic policy,
configurable workspaces, persistent observable background execution, explicit
resume and cleanup, adversarial coverage, dogfood evidence, and reviewed GitHub
releases. No completion claim is made from implementation alone; the release
gates and live installed-plugin trials must also pass.
