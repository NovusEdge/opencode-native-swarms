# v0.1.0 Release and Dogfood Design

Status: Proposed

## Goal

Ship `v0.1.0` as the first GitHub release of OpenCode Native Swarms after the
merged implementation has passed its existing automated checks and five real,
read-only `/swarm` workflows. Protect `main` so future changes arrive through
pull requests whose `Quality` job passes.

This rollout should answer one practical question before stage-two features are
designed: does the current plugin reliably provide useful background research,
review, and narrow verification while the primary OpenCode conversation stays
available?

## Scope

The rollout includes:

- an active GitHub ruleset for `main`;
- five dogfood workflows executed through the installed plugin;
- a concise, committed dogfood report;
- GitHub issues for distinct, reproducible problems found during the trials;
- focused fixes through pull requests when a release-blocking problem is found;
- an annotated `v0.1.0` tag and GitHub release after the release gate passes.

The rollout does not include:

- publishing to npm or another package registry;
- a writing agent or permission expansion;
- a Codex port;
- a declarative workflow language;
- model pinning or changes to the user's model selection;
- broad feature work unrelated to a demonstrated dogfood failure.

## Main-branch ruleset

Create one repository ruleset targeting only `refs/heads/main`. It will:

- require every change to be associated with a pull request;
- require zero approving reviews, avoiding a solo-maintainer deadlock;
- require all review conversations to be resolved;
- require the `Quality` status check and require the branch to be current;
- block branch deletion and non-fast-forward pushes;
- define no routine bypass actor.

GitHub supports requiring a pull request without requiring an approval, and it
identifies workflow status checks by job name, so the required context is the
existing `Quality` job. The ruleset will be verified through the GitHub API
after creation, and a disposable documentation pull request will prove that
the rule is enforced before the release is cut.

Reference: <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets>

## Dogfood workflows

Each trial runs against this repository from a clean worktree using the real
`/swarm` command and the globally installed checkout. The current experimental
background-subagent flag remains enabled. The five objectives are deliberately
different so they exercise every stage-one role and common coordination shape.

1. **Architecture exploration** — map the plugin's configuration, tool, agent,
   and command boundaries; identify the smallest safe extension point for a
   future workflow type.
2. **Change review** — inspect `c3e9bf2..81d702c` for correctness, security, and
   maintainability risks without editing files.
3. **Test triage** — determine the narrow verification commands for the current
   repository, run permitted checks, and explain any failure with evidence.
4. **Documentation verification** — compare the README's installation, usage,
   permissions, and uninstall claims with the implementation and resolved
   OpenCode configuration.
5. **External research** — use current primary OpenCode documentation to check
   the plugin assumptions about custom agents, commands, permissions, and
   background subagents; distinguish documented guarantees from experimental
   behavior.

The exact prompt, start and finish time, workers used, returned evidence,
outcome, and observed friction are recorded for every trial in
`docs/dogfood/v0.1.0.md`. Raw model transcripts are not committed. Before and
after each run, `git status --porcelain` confirms that the read-only swarm did
not change the worktree.

The primary conversation must remain usable while assignments run. A trial is
not considered successful merely because it produces fluent prose: its claims
must point to repository evidence, an executed check, or a current primary
source as appropriate.

## Findings and fixes

Findings are classified as follows:

- **Release blocker:** a permission-boundary escape, unintended write, secret
  exposure, inability to launch background workers, incorrect installation,
  or consistently unusable result. Fix by pull request and rerun the affected
  trial before release.
- **Follow-up defect:** a reproducible correctness or documentation problem that
  does not invalidate the stage-one safety or core workflow. Open a labeled
  GitHub issue; fix before release only when the change is focused and low risk.
- **Enhancement:** desired behavior outside the non-writing stage-one contract.
  Record it as an enhancement issue and defer it to stage-two design.
- **Observation:** subjective friction without a reproducible action. Keep it in
  the dogfood report rather than creating issue noise.

One GitHub issue is created per distinct actionable problem, with reproduction
steps, expected and actual behavior, severity, and a link to the dogfood report.
No secrets, local absolute paths, or raw private transcripts are included.

## Release gate

The `v0.1.0` tag may be created only when all of the following are true:

- all five dogfood trials have completed and are documented;
- no release blocker remains open;
- the tested release commit has a successful `Quality` check;
- `bun run check`, `bun run package:check`, and the full pre-commit suite pass
  locally on the release commit;
- the repository and package version are both `0.1.0`;
- the worktree is clean;
- the active `main` ruleset has been verified;
- installation and uninstall instructions still match actual behavior.

The GitHub release targets the commit containing the dogfood report. Its source
code must be identical to the dogfood candidate; only rollout documentation may
have changed after the trials. The release uses the annotated tag `v0.1.0` and
summarizes stage-one capabilities, safety boundaries, requirements,
installation, and known limitations. This release is GitHub-only.

## Failure and rollback policy

If a trial exposes a blocker, release work pauses while the blocker is fixed in
a pull request. Only the affected trial and any safety-adjacent verification
need to be repeated, followed by the full release gate.

After publication, the `v0.1.0` tag is never moved. A newly discovered defect is
documented and fixed in a later patch release. If the ruleset itself prevents
normal recovery, it may be temporarily disabled through an explicit maintainer
action, then restored and re-verified; it is not deleted as a first response.

## Completion criteria

This rollout is complete when the ruleset is active, the dogfood report is on
`main`, actionable findings are tracked, all release gates pass, and GitHub
shows a public `v0.1.0` release targeting the documented release commit.
Stage-two design begins only after this evidence is available.
